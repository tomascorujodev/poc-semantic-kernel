# Step 4 of poc-semantic-kernel: Agents (Handoff Orchestration)

> **Goal of this step:** split the single assistant into **specialist agents** (triage, orders, policies) that **transfer the conversation** to each other, like a call centre.
>
> **Result:** ✅ Working. `dotnet run -- 4` routes policy questions to `PolicyAgent`, order questions to `OrdersAgent`, and answers "Is order 40 still under warranty?" by combining order data and the warranty document.
>
> 📘 The alternative design (a coordinator that calls agents as tools) is explained in [`step-04-option-a-agents-as-tools.md`](step-04-option-a-agents-as-tools.md).

## 1. What is an agent?

In Steps 2–3 we had **one assistant** with every tool and one long system prompt. That works, but as you add tools and rules:
- the prompt gets long and rules start to conflict,
- the model chooses tools less reliably (more tools = more confusion),
- you can't change one area without risking the others.

An **agent** packages **a name, a description, instructions, a model and its own tools** into one object. In a **multi-agent** system each agent is a specialist with a short, focused prompt and only the tools it needs.

| | Single assistant (Steps 2–3) | Multi-agent (Step 4) |
|---|---|---|
| Prompt | One long prompt with every rule | Short prompt per agent |
| Tools | All tools always available | Each agent sees only its own tools |
| Changing one area | May affect everything | Change one agent |
| Cost / latency | Lower | Higher (more model calls: routing + handoffs) |
| Debugging | One conversation | Must follow messages between agents |

> ⚠️ **Multi-agent is not always better.** For a small assistant like this one, Step 3 already works well. Agents pay off when the domain grows (many tools, different teams owning different areas, different models per task).

### Two common multi-agent patterns

| Pattern | How it works | In this PoC |
|---|---|---|
| **Handoff** | An agent **transfers the conversation** to another agent, who then talks to the user directly (call centre) | ✅ Implemented |
| **Agents as tools** | A coordinator **calls** specialists like functions and writes the final answer itself (manager who delegates) | 📘 Guide only |

Semantic Kernel also has **sequential**, **concurrent**, **group chat** and **magentic** orchestrations, built on the same runtime.

## 2. Key concepts

| Concept | What it is | Where it is in the code |
|---|---|---|
| `ChatCompletionAgent` | An agent backed by a chat model: `Name`, `Description`, `Instructions`, `Kernel`, `Arguments` | `Agents/StoreAgents.cs` |
| **Agent's own kernel** | Each agent gets `kernel.Clone()` with **only its plugins** | `Agents/StoreAgents.cs` |
| `Description` | What *other agents* read when deciding to hand off to this agent | `Agents/StoreAgents.cs` |
| `OrchestrationHandoffs` | The rules: who may transfer to whom, and when | `Demos/HandoffDemo.cs` |
| **Handoff functions** | SK generates a tool per rule (e.g. `transfer_to_PolicyAgent`) plus `end_task_with_summary` | generated by SK (visible in the 🔧 logs) |
| `HandoffOrchestration` | Runs the agents following the handoff rules | `Demos/HandoffDemo.cs` |
| `InProcessRuntime` | The "switchboard" that delivers messages between agents (in this process) | `Demos/HandoffDemo.cs` |
| `ResponseCallback` | Called with each agent message → we print `[AgentName] text` | `Demos/HandoffDemo.cs` |
| `InteractiveCallback` | Called when an agent needs input from the user → this is the chat loop | `Demos/HandoffDemo.cs` |
| `OrchestrationResult.GetValueAsync()` | Waits until an agent ends the task and returns its summary | `Demos/HandoffDemo.cs` |

> ℹ️ **Handoff is just function calling.** "Transfer to PolicyAgent" is a tool call like `Orders.GetOrder` in Step 2. Everything you learned about descriptions and `FunctionChoiceBehavior.Auto()` applies.

## 3. Architecture of this step

```
                           ┌────────────────────────────┐
     User ── question ────►│ TriageAgent                │  no plugins: it can only route
                           │ "who should handle this?"  │
                           └─────┬───────────────┬──────┘
               transfer_to_      │               │      transfer_to_
               OrdersAgent       ▼               ▼      PolicyAgent
         ┌───────────────────────────┐   ┌──────────────────────────────────┐
         │ OrdersAgent               │◄─►│ PolicyAgent                       │
         │ plugins:                  │   │ plugins:                          │
         │  Orders (all 3 functions) │   │  Docs.SearchPolicies (RAG)        │
         │  Time                     │   │  Orders.GetOrder  (read-only)      │
         └───────────────────────────┘   │  Time                             │
                     │                   └──────────────────────────────────┘
                     └──── both can transfer back to TriageAgent ─────┘
                                  │
             any agent can call end_task_with_summary → "✔ Task completed"

     All agents run on InProcessRuntime and share the conversation MESSAGES
     (not each other's tool results — see Troubleshooting #1).
```

### Handoff rules

| From | To | When |
|---|---|---|
| TriageAgent | OrdersAgent, PolicyAgent | (uses each agent's `Description`) |
| OrdersAgent | PolicyAgent | Customer asks about returns, warranty or shipping policies |
| OrdersAgent | TriageAgent | Request is not about orders or policies |
| PolicyAgent | OrdersAgent | Customer wants to cancel an order or list their orders |
| PolicyAgent | TriageAgent | Request is not about orders or policies |

## 5. The code explained

### 5.1 An agent (`Agents/StoreAgents.cs`)

```csharp
public static ChatCompletionAgent CreateOrders(Kernel kernel, OrdersPlugin ordersPlugin)
{
    var agentKernel = kernel.Clone();                       // own kernel...
    agentKernel.Plugins.AddFromType<TimePlugin>("Time");     // ...with only its own plugins
    agentKernel.Plugins.AddFromObject(ordersPlugin, "Orders");

    return new()
    {
        Name = "OrdersAgent",
        Description = "Looks up customer orders and cancels orders.",   // read by OTHER agents
        Instructions = """
            You handle questions about specific orders of an electronics store.
            ...
            You do NOT know the store's policies ... and must never ask the customer about them.
            For any policy question ... transfer to PolicyAgent: it can look up the order itself.
            """,
        Kernel = agentKernel,
        Arguments = AutoFunctionCalling(),   // FunctionChoiceBehavior.Auto(), Temperature 0.2
    };
}
```
- **`Instructions`** = the agent's system prompt.
- **`Description`** = the agent's "job title". The orchestration uses it to describe the `transfer_to_OrdersAgent` function to the other agents.
- **`kernel.Clone()`** copies the services (chat model, embeddings) and the **filters** (so the `LoggingFilter` works in every agent), but gives each agent its own plugin collection.
- **TriageAgent has no plugins.** It *cannot* answer questions itself, so it must route. Removing tools is a stronger guarantee than writing "don't answer" in the prompt.

### 5.2 Read-only tool sharing (`CreatePolicy`)

```csharp
var orders = KernelPluginFactory.CreateFromObject(ordersPlugin, "Orders");
agentKernel.Plugins.AddFromFunctions("Orders", [orders["GetOrder"]]);
```
PolicyAgent gets **only `GetOrder`** from the Orders plugin: it can read an order to apply a policy, but it can't cancel. This is the **principle of least privilege** applied to agents. Both agents share one `OrdersPlugin` instance, so they see the same data (a cancellation is visible to both). Why this was needed: see [Troubleshooting #1](#7-troubleshooting-problems-we-hit-and-how-we-fixed-them).

### 5.3 Handoff rules (`Demos/HandoffDemo.cs`)

```csharp
var handoffs = OrchestrationHandoffs
    .StartWith(triage)
    .Add(triage, orders, policy)
    .Add(orders, policy, "Transfer to this agent if the customer asks about returns, warranty or shipping policies")
    .Add(orders, triage, "Transfer to this agent if the request is not about orders or policies")
    .Add(policy, orders, "Transfer to this agent if the customer wants to cancel an order or list their orders")
    .Add(policy, triage, "Transfer to this agent if the request is not about orders or policies");
```
- `StartWith(triage)`: every task starts with TriageAgent.
- Each `.Add(from, to, description)` becomes a function in the *from* agent: `transfer_to_<to>`, with that description. Without a description, the target agent's `Description` is used.
- The rules are also a **safety boundary**: an agent can only transfer where a rule allows it.

### 5.4 The orchestration and callbacks

```csharp
var orchestration = new HandoffOrchestration(handoffs, triage, orders, policy)
{
    ResponseCallback = response =>          // every agent message
    {
        Console.WriteLine($"[{response.AuthorName}] {response.Content}");
        return ValueTask.CompletedTask;
    },
    InteractiveCallback = () =>             // an agent needs the user's input
    {
        var reply = Console.ReadLine();
        return ValueTask.FromResult(new ChatMessageContent(AuthorRole.User, reply));
    },
};
```
- Unlike Steps 2–3, **the orchestration owns the conversation loop**. Our code doesn't decide who answers; it only provides input (`InteractiveCallback`) and shows output (`ResponseCallback`).
- `AuthorName` tells us which agent is speaking.
- There is also a `StreamingResponseCallback` for token-by-token output (not used here, to keep the code simple).

### 5.5 Running it

```csharp
await using var runtime = new InProcessRuntime();
await runtime.StartAsync();

var result = await orchestration.InvokeAsync(input, runtime);  // starts the task
var summary = await result.GetValueAsync();                    // waits until an agent ends it
await runtime.RunUntilIdleAsync();
```
- **A task ends** when an agent calls the built-in `end_task_with_summary` function (e.g. when the customer says goodbye). The summary is returned by `GetValueAsync()`.
- **`InProcessRuntime`** runs everything in one process. The same orchestration code could run on a distributed runtime, with agents in different processes or machines. That's why agents talk through a runtime instead of calling each other directly.
- A `try/catch` handles **HTTP 429** (rate limit) so the app shows a message instead of crashing ([Troubleshooting #2](#7-troubleshooting-problems-we-hit-and-how-we-fixed-them)).

## 7. Troubleshooting: problems we hit and how we fixed them

| # | Problem | Cause | Fix |
|---|---|---|---|
| 1a | "Is order 40 still under warranty?" → OrdersAgent got the order, then **asked the customer** "Could you confirm the duration of the warranty period?" | OrdersAgent didn't know it should hand off policy questions it couldn't answer | Instructions: *"You do NOT know the store's policies and must never ask the customer about them… transfer to PolicyAgent."* |
| 1b | After 1a: OrdersAgent called `GetOrder`, then transferred **without writing anything**, and PolicyAgent said it needed the order details (and transferred back) | **In a handoff, agents share the conversation *messages*, not each other's *tool results*.** The `GetOrder` result stayed inside OrdersAgent's own history. | **Design fix, not a prompt fix:** give PolicyAgent a **read-only** `Orders.GetOrder` (+ `Time`), so it looks up the order itself. Only OrdersAgent can cancel. |
| 2 | `Unhandled exception ... HTTP 429 (too_many_requests: rate_limit_exceeded)`, and the app crashed | Four multi-agent test runs in a row used up the deployment's tokens-per-minute quota. Each question needs several model calls (triage + handoff + tools + answer). | Catch `HttpOperationException` with status 429 in `HandoffDemo` and show a friendly message. Long-term: raise the quota in Foundry, or add retry with back-off. |
| 3 | Build error: `The process cannot access the file ... PocSemanticKernel.exe because it is being used by another process` | A previous `dotnet run` was still open, locking the `.exe` | Close the running app (type `exit`) before building |

## 8. Limitations of this design

- **Memory is per task.** After `✔ Task completed`, the next question starts a **new** orchestration, and the agents forget the previous task. Within one task, the full conversation is kept.
- **Tool results are private to each agent** (Troubleshooting #1b). If agents need to share facts, either give them the tools, or make the agent **write the facts in its message** before handing off.
- **More model calls = more cost and latency** than the single assistant of Step 3, and more exposure to rate limits (429).
- **Confirmation before cancelling is still a prompt rule.** A filter that requires explicit approval before `Orders.CancelOrder` would make it a hard rule.
- **Preview packages:** the orchestration API may change in future SK versions. Microsoft's newer **Agent Framework** has similar concepts (agents, handoff, workflows).

---

## 9. Lessons learned
- **An agent = instructions + tools + model.** Most of the design work is deciding **which tools each agent gets**.
- **Handoff is function calling.** SK turns the rules into `transfer_to_X` tools, and the model calls them like any other tool.
- **Restrict with tools, not only with words.** TriageAgent can't answer because it has no tools; PolicyAgent can't cancel because it only has `GetOrder`.
- **Agents share messages, not tool results.** This is the most important multi-agent debugging lesson from this PoC.
- **Prompt fixes vs design fixes.** Fix 1a (prompt) helped but wasn't enough; fix 1b (tool design) solved it reliably.
- **Multi-agent costs more.** Use it when specialisation is worth the extra calls.

## 10. Glossary

| Term | Definition |
|---|---|
| **Agent** | A model + instructions + tools, with a name and a description, that can act on its own |
| **Multi-agent system** | Several agents that collaborate on a task |
| **Orchestration** | The pattern that decides how agents work together (handoff, sequential, concurrent, group chat…) |
| **Handoff** | Transferring the conversation from one agent to another |
| **Triage** | The first step that classifies a request and routes it |
| **Runtime** | The component that delivers messages between agents |
| **Interactive callback** | Where the orchestration asks the human for input (human-in-the-loop) |
| **Least privilege** | Giving each component only the permissions (tools) it needs |
| **Rate limit (429)** | Azure refuses requests when the deployment's tokens/requests per minute quota is exceeded |
